# 工程原則

## 品質信心來自多層證據

單一指標不能證明軟體正確。可靠的品質關卡應把不同失敗模式交給不同機制檢查：

- 單元與整合測試驗證已知行為與模組協作。
- Gherkin 把關鍵需求與邊界條件變成可執行規格。
- CLI smoke 從使用者可見邊界驗證真正的執行路徑。
- coverage 找出未執行區域，但不把覆蓋率誤當正確率。
- mutation testing 主動改變程式語意，檢查測試是否真的能偵測錯誤。
- complexity、module size 與 dependency contracts 約束測試以外的結構風險。

## 人與自動化的責任邊界

自動化先提供可重現的失敗證據，再縮小人工判斷範圍。人仍負責：

- 確認需求與驗收 oracle 是否真實且完整。
- 找出容易被實作者與測試共同忽略的邊界條件。
- 依 criticality 決定 Quick、Full 或 Mutation gate。
- 審查安全、法遵、架構取捨與不可逆操作。
- 對發布與事故處理承擔最終責任。

因此，「不逐行閱讀所有產出」不等於取消 code review 或免除責任。審查深度應依風險調整，機械證據也不能取代領域專家。

## 指標的正確用法

- Coverage 只證明程式曾被執行，不能證明 assertion 正確。
- Mutation survivor 表示現有測試未察覺某個工具產生的語意變更；零 survivor 仍不是完整正確性證明。
- 複雜度與模組大小是可維護性警訊，不是設計品質的唯一尺度。
- 所有門檻採 fail closed：報告缺失、樣本為零或格式無法解析都不得視為通過。
- 指標必須和行為規格、架構契約及人工風險判斷一起使用，避免為分數而優化。

## 分層驗證

快速回饋與深度驗證應分開。一般迭代先跑 Quick gate；完整交付跑 Full gate並產生機械可讀 evidence；高風險核心規則、排程驗收或合併前再追加 Mutation gate。這能兼顧回饋速度與缺陷偵測能力，而不是每次變更都無差別執行最昂貴的檢查。
